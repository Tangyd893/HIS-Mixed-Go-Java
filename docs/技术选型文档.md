# HIS-Mixed 技术选型文档

> Java + Go 混合架构 HIS 医院信息系统的技术选型说明

---

## 一、选型总览

### 1.1 为什么选择 Java + Go 混合架构

| 维度 | Go | Java |
| ---- | -- | ---- |
| **并发模型** | 协程（goroutine），轻量级，万级并发 | 线程（Thread），重量级，数百并发 |
| **内存占用** | 低（单服务 10-50MB） | 较高（单服务 200-500MB） |
| **启动速度** | 毫秒级 | 秒级（Spring Boot 5-15s） |
| **事务支持** | 需第三方库（GORM 事务） | 成熟（Spring 声明式事务、Seata 分布式事务） |
| **ORM 生态** | GORM（成熟度 7/10） | MyBatis-Plus / JPA（成熟度 10/10） |
| **安全框架** | 需自建（golang-jwt + 中间件） | Spring Security（开箱即用） |
| **报表引擎** | 需自建 | JasperReports / POI 成熟方案 |
| **人 才市场** | 增长快，基数小 | 存量最大，招聘容易 |

**核心决策**：让两种语言各自做最擅长的事，而非用一种语言覆盖所有场景。

### 1.2 选型原则

| 原则 | 说明 |
| ---- | ---- |
| **场景匹配** | 高并发 I/O → Go，复杂事务 → Java |
| **生态成熟** | 优先选择社区活跃、文档完善的方案 |
| **一致性** | 跨语言交互使用 gRPC + Protobuf 统一契约 |
| **可运维** | 所有组件 Docker 化，统一通过 Nacos 服务发现 |

## 四、基础设施

### 4.1 数据库

| 组件 | 选型 | 版本 | 说明 |
| ---- | ---- | ---- | ---- |
| 主数据库 | PostgreSQL | 17 | 支持 JSON/JSONB、全文检索等高级特性，Database per Service |
| 缓存 | Redis | 7 | 号源缓存、分布式锁、会话管理、排队队列 |
| 消息队列 | RabbitMQ | 4.0 | 异步解耦、削峰填谷、支持 Quorum Queue |
| 对象存储 | MinIO | latest | 兼容 S3 协议，检查影像/附件存储 |

### 4.2 基础设施选择理由

| 中间件 | 选型理由 |
| ------ | -------- |
| **PostgreSQL** | 相比 MySQL 支持更丰富的数据类型（JSON/JSONB/数组），医疗数据半结构化场景更合适；MVCC 机制适合高并发 |
| **Redis** | 号源扣减、排队叫号、分布式锁等场景的核心依赖；Sorted Set 天然适合排队场景 |
| **RabbitMQ** | 相比 Kafka，RabbitMQ 更擅长复杂路由和业务消息可靠性；Quorum Queue 保证消息不丢失 |
| **Nacos** | 同时支持服务注册发现和配置中心，Java 和 Go 均有 SDK 支持，生态统一 |
| **MinIO** | S3 兼容、高性能、轻量部署，适合医疗影像和文档存储 |

## 五、跨语言通信

### 5.1 同步调用：gRPC + Protobuf

| 选型 | 理由 |
| ---- | ---- |
| **Protobuf** | 强类型、二进制序列化（比 JSON 小 5-10 倍）、支持多语言代码生成 |
| **gRPC** | HTTP/2 多路复用、双向流、连接池、拦截器生态成熟 |
| **共享 proto** | Java 和 Go 共享同一份 `.proto` 文件，作为唯一 API 契约 |

**代码生成**：

```bash
# Go 端
protoc --go_out=. --go-grpc_out=. proto/**/*.proto

# Java 端
protoc --java_out=java/common/src/main/java proto/**/*.proto
```

### 5.2 异步协作：RabbitMQ

| 优势 | 说明 |
| ---- | ---- |
| **多语言支持** | Java (Spring AMQP) 和 Go (amqp091-go) 均有成熟客户端 |
| **消息可靠性** | 交换机/队列/消息持久化 + Publisher Confirm + 手动 ACK |
| **复杂路由** | Topic 交换机支持通配符路由，灵活匹配业务场景 |
| **Quorum Queue** | 基于 Raft 协议，消息不丢，替代传统镜像队列 |

### 5.3 统一服务发现：Nacos

| 角色 | 实现方式 |
| ---- | -------- |
| Java 端 | `spring-cloud-starter-alibaba-nacos-discovery` 自动注册 |
| Go 端 | Nacos Go SDK 手动注册与健康检查 |
| 发现 | 双方通过 Nacos 查询对方服务地址，gRPC 直连调用 |

## 十一、选型总结

### 核心收益

| 收益点 | 说明 |
| ------ | ---- |
| **网关 QPS 提升** | Go Gin 网关替代 Spring Cloud Gateway，预期 QPS 提升 5-10 倍 |
| **内存开销降低** | Go 服务内存占用为 Java 服务的 1/5 ~ 1/10 |
| **高并发优化** | 挂号/药房/检查等高频服务用 Go 协程处理，无需复杂线程池调优 |
| **复杂业务保障** | Spring Boot + MyBatis-Plus + Seata 保障处方/收费/住院等复杂事务 |
| **安全认证复用** | Spring Security RBAC 体系保留在 Java 侧，Go 侧仅做 JWT 解析 |
| **运维统一化** | Nacos 统一注册、RabbitMQ 统一消息、Docker 统一部署 |

### 风险与缓解

| 风险 | 缓解措施 |
| ---- | -------- |
| 跨语言 gRPC 调试复杂 | 统一 proto 文件，使用 grpcurl/kreya 工具调试 |
| 两套代码规范维护成本 | CI 中集成 gofmt + checkstyle，统一提交规范 |
| Go 生态不如 Java 成熟 | 医疗核心（EMR、处方）保留在 Java 侧 |
| 团队技能要求高 | Go 部分参考 HIS-Go 项目，降低上手门槛 |
